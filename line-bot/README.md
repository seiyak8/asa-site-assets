# ASA 自動化スクリプト（Google Apps Script）

Queue 用スプレッドシートにバインドされた Apps Script プロジェクトの中身。
このリポジトリは版管理のためのミラー。**編集したら Apps Script 側にも反映すること。**

| ファイル | 役割 |
|---|---|
| `Code.gs` | LINE 公式アカウントの自動応答（日本語 / English / ภาษาไทย） |
| `MetaInsights.gs` | Meta広告と Instagram の実績を毎日取り込み、シートに蓄積 |

貼り付け用のページ（コピーボタン付き）は `reports/build-code-viewer.py` が生成する。

## 最優先：チャネルアクセストークンの再発行

修正前のコードには、チャネルアクセストークンが **平文で5箇所** 書かれていた
（`setProperties` の `TOKEN` 定数、`processQueue` のログ出力、`checkProperties` の

1. LINE Developers → 対象チャネル → Messaging API設定 → チャネルアクセストークンを再発行
2. GASエディタ → 左の歯車「プロジェクトの設定」→ スクリプト プロパティ に登録
   - キー `LINE_CHANNEL_ACCESS_TOKEN` … 新しいトークン
   - キー `QUEUE_SHEET_ID` … `1WGIH9RSUQYiohj9wT2yuk9Py8qOHUpMrYYxlnec8tFk`
3. コードには二度と書かない。`Code.gs` からは `setProperties()` 関数ごと削除済み

## 直した不具合

### 1. スクリプトプロパティの読み方が間違っていた（これが原因で全体が停止）

```js
// 修正前 — スプレッドシートIDを「キー」として渡していた
const id = PropertiesService.getScriptProperties()
             .getProperty('1WGIH9RSUQYiohj9wT2yuk9Py8qOHUpMrYYxlnec8tFk');
```

`setProperties()` はこの値を `QUEUE_SHEET_ID` というキーで保存している。
上の呼び方では `null` が返り、`SpreadsheetApp.openById(null)` が例外を投げる。

`getQueueSheet_()` と `getKnownContactsSheet_()` の両方が同じ間違いをしていたため、
**キューへの追加も定時送信も、すべて例外で止まっていた。** 同じファイル内の
`debugListSheetNames()` だけは正しく `'QUEUE_SHEET_ID'` を使っており、
書き換えの取りこぼしだったことが分かる。

修正：キー名を定数 `PROP_SHEET_ID` / `PROP_TOKEN` に集約し、未設定なら
何が足りないかを明示した例外を投げるようにした。

### 2. フォームからLINEユーザーIDを取り出せなかった

```js
// 修正前 — 'システム用ID' と 'system id' しか探していない
return k.indexOf('システム用ID') !== -1 || k.toLowerCase().indexOf('system id') !== -1;
```

体験フォームの回答シートの列名は実際には **`LINE ID`**。一致しないので
`extractUserId_` が `null` を返し、**シーン2（持ち物案内）は一度も送られていなかった。**

修正：`システム用ID` / `system id` / `LINE ID` / `line_id` などの表記ゆれを許容。

### 3. 問い合わせへの返信が最大1時間遅れていた

シーン1はキューに積まれ、1時間おきの `processQueue` で送られていた。
体験の問い合わせに1時間沈黙するのは、そのまま申込率に響く。
7月にLINEへ6名から問い合わせがありながら体験申込が0件だったことと無関係ではない。

修正：`REPLY_MODE = 'immediate'` を既定にし、**受信したその場で返信**するようにした。
スタッフが全件を事前確認したい運用に戻す場合は `'queue'` に変えるだけでよい。

### 4. プッシュ送信で無料枠を消費していた

すべての送信が `/message/push` だった。受信メッセージへの応答は `replyToken` を
使った `/message/reply` で送れば**送信数の上限を消費しない**。
修正：受信への応答は `replyMessage_()`、フォーム送信後の案内など
こちらから送るものだけ `pushMessage_()` を使う。

### 5. 持ち物案内が二重に送られ得た

利用者が「完了しました」と送った場合と、フォーム送信トリガーが動いた場合の
両方でシーン2が送られていた。修正：どちらの経路も `alreadyHandled_()` を通す。

### 6. エラーで後続のイベントが落ちていた

`events.forEach` の中で例外が出ると、同じリクエストに含まれる残りのイベントが
処理されなかった。修正：1件ずつ `try/catch` で囲んだ。

## 加えた機能

**言語の記憶（`UserLang` シート）**
文字種だけで判定すると、タイ在住の方が英語で書いた瞬間に英語扱いになる。
一度でもタイ語でやり取りした相手は、以後タイ語で応対する。
「日本語」「English」「ภาษาไทย」と送れば手動で切り替えられる。

**言語判定の順序を直した**
記憶を優先しすぎて、日本語で問い合わせた方が次に英語で書き直しても
日本語で返していた（`I want to refund` に `human_handoff_ja` が立っていた）。
英語に切り替えるのは「日本語では通じなかったかもしれない」と思われたときなので、
そこで日本語を返すのが一番まずい。判定は次の順になった。

1. 言語を名指しした依頼（「日本語でお願いします」「in Thai」）
2. 文字種（タイ文字・かな）
3. **ヒント語が2語以上当たった言語**（← ここを記憶より前に入れた）
4. そのお客様の前回の言語
5. 漢字があれば `ja`、なければ `en`

3 の閾値を2語にしてあるのは、「OK」「thanks」程度の相槌で日本語のお客様が
英語扱いにならないようにするため。ローマ字書きの日本語（`taiken ikura desu ka`）と
タイ語（`sawasdee kha yak sonjai rian`）もここで拾う。

**人が対応すべき内容の切り分け**
返金・解約・退会・クレーム・怪我・値引きに触れるメッセージは自動で答えず、
3言語で「担当者からご連絡します」と返し、Queue の担当者欄に `要対応` を立てる。
子どもの習い事で、料金や安全に関わる話を推測で答えさせないための線引き。

**人が応対したお客様には自動送信しない**

体験まで来て、双子のお子さんのことで代表と何度もやり取りしていたお客様に
「初めまして！」の初回案内が飛び、代表が「誤送信失礼いたしました」と
謝る事故が起きた。お客様の「ぜひ**申し込み**たいのですが」という一文が
シーン1のキーワードに当たったため。

`isKnownContact_` という防御は元からあったが、**`KnownContacts` シートが空**で
誰も登録されておらず、かつシーン1にしか掛かっていなかった。登録は手作業で、
しかも**ボットはLINE公式アカウントマネージャー上の手動のやり取りを見られない**
（webhookに流れてこない）ため、「人が応対したか」を後から知る手段がない。

そこで判定を逆にした。

> **友だち追加の瞬間をボットが記録できている人だけ**に自動送信する。

いつからいるのか分からない相手には送らない。判定は `handleEvent_` の
**先頭**（キーワードの判定より前）に1か所だけ置き、通り抜ける経路を作らない。

| シート | 役割 |
|---|---|
| `Followers` | 友だち追加を記録できた人。**この人たちだけ**が自動送信の対象 |
| `NoAutoReply` | 自動送信しない人。一度載ると外れない |

貼り替え後に **`markAllCurrentFollowersAsExisting()` を一度だけ実行**する。
いま友だちである全員が `NoAutoReply` に入り、既存のお客様がまとめて保護される。
一覧APIが使えないアカウントでも、「友だち追加を記録していない人には送らない」
規則が働くので、既存のお客様に初回案内が飛ぶことはない。

止まったメッセージは `Queue` に `skipped_known_customer` として記録され、
担当者欄に `要対応` が立つ。**無視されるのではなく人に回る。**

フォーム送信をきっかけにした送信も止まる（`BLOCK_ON_FORM_SUBMIT = true`）。
その代わり、止まった案内はスプレッドシートの **ASAツール** メニューから
人が選んで送る。

| メニュー | 送るもの | 送るタイミング |
|---|---|---|
| ① 持ち物案内を送信 | シーン2 | 体験フォームの記入後 |
| ② 体験後のお礼を送信 | シーン3 | 体験レッスンの後 |
| ③ Band招待を送信 | シーン4 | 入会フォームの記入後 |

手動送信は禁止リストを見ない（送る相手も文面も人が決めているため）。
送信済みの記録があるときは、送る前に確認を出す。二重送信は
「話を聞いていない」という印象になるので黙って通さない。

**送信するとそのお客様は自動送信の禁止リストに入る。** 人が応対を始めた
相手なので、以後ボットが割り込まないようにしている。

**文面の出典は「Academy LINE Response Manual」**
シーン1〜4の本文はこのマニュアルが原本。**先にマニュアルを直してからコードに写す。**
逆順にすると、スタッフが手で送る文面とボットが送る文面が食い違う。

タイ語は話し手の性別で語尾が変わるため、シーン2・3・4を `{ female, male }` の
2種類で持っている。手動送信のときは送るスタッフの性別を尋ね、**自動送信のときは
実在の話し手がいないので女性形**を使う（`resolveBody_()`）。

シーン2には Future Steps International School の会場案内（階段を上がった2階、
実質3階の体育館）が入っている。当日「体育館が見つからない」で始まる体験は
取り返しがつかないので、文面を触るときに落とさないこと。

**初回案内にクラススケジュールの画像を添える**
「一番早い体験はいつですか」は最初の問い合わせでよく聞かれる。曜日・時間・場所を
先に見せておけば、人が答えるまでの待ち時間が申込率を削らずに済む。
シーン1の案内文の直後に、その言語のスケジュール画像を1枚送る。

画像は `assets/images/schedule-{ja,en,th}.jpg` に置き、
`raw.githubusercontent.com` の公開URLをそのまま参照している。

| 条件 | 理由 |
|---|---|
| 公開HTTPS | 認証を要求するURLは不可。**Googleドライブの共有リンクは使えない**（画像ではなくHTMLを返すため） |
| JPEG か PNG | LINEの仕様 |
| 1MB以下 | `previewImageUrl` の上限。1ファイルで original と preview を兼ねるため |

画像を差し替えたら **`testScheduleImages()`** を実行し、3言語とも `OK` になることを
確認する。URLが切れたまま送ると、LINEは配列ごと拒否するので**案内文すら届かない**。
その事故を防ぐため、画像付きの送信が失敗したらテキストだけで自動的に送り直す。

**キーワードの拡充**
タイ語は `ทดลอง` `สมัคร` の2語しかなく、「สนใจ（興味があります）」のような
自然な問い合わせに反応できなかった。英語も同様。3言語とも実際の言い回しを追加した。

さらに、料金・日時・場所・年齢・種目といった実際に多い聞き方を3言語に足した。
「駐車場はありますか」「Where are you located?」「ค่าเรียนเท่าไหร่คะ」のような、
体験の申し込みにつながる質問が無反応にならないようにしている。

エスカレーション語（人に回す語）も増やしたが、こちらは**増やしすぎると
体験の申し込みまで人待ちになって申込率が落ちる**ので、答えを間違えると実害が出る
話——お金・退会・苦情・怪我・体調——に限っている。次の語は意図的に外した。

| 外した語 | 理由 |
|---|---|
| `熱` | 「情熱」「熱心」に当たる。発熱は `発熱` で拾う |
| `謝` | 「感謝しています」に当たる。`謝罪` で拾う |
| `stop` | 「What time does the class stop?」に当たる |
| `charge` | 「How much do you charge?」は料金の質問で、人手は要らない |
| `แพ้` | タイ語では「試合に負ける」の意味にもなる。`แพ้อาหาร` で拾う |

**キーワードの動作確認（`keyword-test.js`）**
キーワードを触ったら、GASに貼り替える前に手元で実行する。

```
node line-bot/keyword-test.js
```

`Code.gs` をそのまま読んで判定関数だけを動かす。スプレッドシートもLINEも
触らないので、実行しても誰にも何も送らない。48件を確認していて、
「当たるべき」だけでなく「**当たってはいけない**」（`感謝しています` が
エスカレーションしない、`How much do you charge?` が人待ちにならない）も見ている。

**タイ語の語尾を性別に対応させた**
タイ語の `ครับ` / `ค่ะ` は聞き手ではなく**話し手**の性別を表す。修正前は全文が
`ครับ`（男性話者）で固定されていた。

- **自動返信（シーン1・2・4、エスカレーション文）は女性形 `ค่ะ` に統一。**
  送信するのはアカデミーであって個人ではないため、ブランドの声として一つに定める。
  `นะ` の後は `นะคะ` になる点も揃えた。
- **シーン3だけは送信者の性別を選べる。** これはスタッフが手動で送るもので、
  実在の話し手がいるため。メニューから言語に `th` を選ぶと性別を尋ねられ、
  `f`（女性）なら `ค่ะ / นะคะ`、`m`（男性）なら `ครับ / นะครับ` で送られる。
  日本語・英語では尋ねない。

## セットアップ手順

1. スクリプトプロパティに `LINE_CHANNEL_ACCESS_TOKEN` と `QUEUE_SHEET_ID` を設定
2. `checkProperties()` を実行し、両方が表示されることを確認
3. `testSheetAccess()` を実行して権限を承認
4. ウェブアプリとしてデプロイし、そのURLを LINE Developers の Webhook URL に登録
5. `setupFormTriggers()` を実行（「登録成功」が5件出ることを確認）
6. `setupHourlyTrigger()` を実行（送信漏れの再送用。即時返信でも保険として残す）

## 動作確認

**先に異常系から確認すること。**

1. 「返金してほしい」を3言語で送る → 自動回答せず、担当者欄に `要対応` が立つ
2. 「体験を希望します」を日本語・英語・タイ語で送る → その言語で即座に返信が来る
3. 同じ人がもう一度同じことを送る → 二度目は送られない
4. 一度タイ語で会話した人が英語で送る → タイ語のまま応対される
5. 体験フォームを送信 → 持ち物案内が届き、`LINE ID` 列に値が入っている
6. フォーム送信後に「完了しました」と送る → 持ち物案内は重複しない

# MetaInsights.gs — 広告と Instagram の実績取得

Windsor.ai の置き換え。無料プラン（`plan_id: FREE`）では接続を1アカウントまで
減らしてもデータが返らないことを確認したため、Meta Graph API を直接叩く形にした。
費用はかからない。

## なぜ Apps Script に置くか

Claude の実行環境からは `graph.facebook.com` に到達できない（ネットワークポリシーで
遮断）。Google のサーバーから叩く必要がある。

副次的に、日次でシートに貯めるので**履歴が残る**。Windsor.ai は都度問い合わせるだけで
過去との比較ができなかった。週次レポートは Google ドライブ経由でこのシートを読むため、
レポート側の仕組みは何も変えなくてよい。

## 追加するスクリプトプロパティ

| キー | 値 |
|---|---|
| `META_ACCESS_TOKEN` | システムユーザーの長期トークン |
| `META_AD_ACCOUNT_ID` | 広告アカウントID（先頭の `act_` は付けなくてよい） |
| `META_IG_USER_ID` | `17841461840431729`（ASA公式。Windsor.ai の調査で判明済み） |

**トークンはチャットに貼らず、直接スクリプトプロパティに保存すること。**

## トークンの発行（社長の作業）

通常のユーザートークンは60日で失効する。**システムユーザートークンは失効しない**ので、
そちらを使う。

1. business.facebook.com → ビジネス設定 → ユーザー → システムユーザー → 追加
2. そのシステムユーザーに**アセットを割り当て**（ASAの広告アカウント、Instagramアカウント）
3. 「新しいトークンを生成」で以下の権限を付ける
   - `ads_read` … 広告の実績
   - `instagram_basic` / `instagram_manage_insights` … Instagram
   - `pages_read_engagement` … IGはFacebookページ経由で紐付くため

## 実行の順序

1. `testMetaConnection()` … **まずこれ。** 広告アカウント名と Instagram ユーザー名が
   返るか、どの指標が取れるかを確認する
2. `backfillMeta(90)` … 過去90日を投入して履歴を作る
3. `setupMetaTriggers()` … 毎日の自動取得を登録（広告5時台 / Instagram 6時台）

## 作られるシート

| タブ | 列 |
|---|---|
| `MetaAds` | date / campaign / spend / impressions / reach / clicks / cpc / ctr / fetchedAt |
| `InstagramDaily` | date / reach / profileViews / followers / fetchedAt |

`date + campaign` をキーに**上書き**するので、再実行しても行が重複しない。

## 設計上の判断

**エラーをゼロで埋めない。** トークン切れや権限不足で取得できなかったとき、0を書くと
レポートを読む側が「広告費を使わなかった」と誤読する。「使っていない」と「測れない」は
経営判断上まったく別なので、例外として止める。Windsor.ai のプラン上限メッセージを
危うくゼロと報告しかけた反省から。

**Instagram の指標は仕様変更が多い。** `impressions` は2025年に廃止され `views` に
なった。取れなかった指標は0で埋めず空欄にし、ログに記録して処理は続ける。
実際に何が返るかは `testMetaConnection()` で確かめること。

**APIバージョンは `v21.0` に固定。** 既定に任せると予告なく上がる。
